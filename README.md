## 4. Решение задания 1 — сущность `Product`

`Product` хранит ID, название и цену в закрытых полях. Конструктор и `SetPrice` используют централизованные проверки, поэтому отрицательная цена не может попасть в объект через публичный контракт. Публичные методы предоставляют только необходимые операции чтения и изменения цены; сам класс не выводит данные в консоль.

**Файл:** `Marketplace.Domain/Product.cs`

```csharp
public sealed class Product
{
    private readonly int id;
    private readonly string title;
    private int price;

    public int GetId() => id;
    public string GetTitle() => title;
    public int GetPrice() => price;

    public void SetPrice(int newPrice)
    {
        ValidatePrice(newPrice);
        price = newPrice;
    }

    // Конструктор, GetInfo и приватные Validate... находятся
    // в полном исходном файле Product.cs.
}
```

В `Program.cs` проверяется `SetPrice(-100)`. Вызов выбрасывает `ArgumentOutOfRangeException`, который перехватывается демонстрационным методом `RunValidationCheck`. Дополнительно проверяется, что после отказа цена товара осталась прежней.

## 5. Решение задания 2 — каталог `Catalog`

`Catalog` хранит товары в закрытом `List<Product>`. Добавление проверяет `null` и дубликаты по названию без учёта регистра и пробелов по краям. `Find` и `Remove` используют нормализацию названия. `GetProducts()` возвращает отдельную копию, обёрнутую в read-only коллекцию, поэтому вызывающий код не может изменить внутренний список каталога.

**Файл:** `Marketplace.Domain/Catalog.cs`

```csharp
private readonly List<Product> _products = new();

public IReadOnlyList<Product> GetProducts()
{
    return _products.ToList().AsReadOnly();
}

public int GetCount() => _products.Count;
```

В точке входа дополнительно проверяются:
- `Add(null!)` — выбрасывает `ArgumentNullException`;
- поиск отсутствующего товара — возвращает `null`;
- удаление отсутствующего товара — возвращает `false`;
- повторное название с другими пробелами и регистром — отклоняется как дубликат.

## 6. Решение задания 3 — доступ к данным и DIP

`IProductRepository` — публичная абстракция хранения. `FileProductRepository` — `internal` реализация, которая сохраняет товары в файл и восстанавливает их. Формат строки: `ID;Цена;НазваниеBase64`; название кодируется в Base64, чтобы разделитель `;` внутри названия не ломал структуру записи. Если файла нет, `Load()` возвращает пустой список.

**Файлы:** `Marketplace.DataAccess/IProductRepository.cs`, `Marketplace.DataAccess/FileProductRepository.cs`.

Ключевой фрагмент точки входа:

```csharp
IProductRepository repository = new FileProductRepository(filePath);
repository.Save(catalog.GetProducts());

List<Product> loadedProducts = repository.Load();
```

Переменная объявлена через `IProductRepository`, поэтому клиентский код обращается к контракту интерфейса, а не к конкретным методам реализации. Конкретный файловый репозиторий создаётся в точке композиции приложения. Это демонстрация DIP на уровне учебного консольного приложения.

## 7. Решение задания 4 — вывод, форматирование и отчёт (SRP)

`CatalogPrinter` отвечает за печать списка и самых дорогих товаров. `PrepareLine` подготавливает строку, а `PriceFormatter` объявлен в том же файле с модификатором `file`, поэтому недоступен из `CatalogReport.cs` и других файлов. `CatalogReport` отдельно выполняет вычисления и возвращает текст сводки; он не печатает в консоль и не обращается к файлам.

**Файлы:** `Marketplace.Presentation/CatalogPrinter.cs`, `Marketplace.Presentation/CatalogReport.cs`.

### Единый формат цены

Для единообразия используется культура `ru-RU` и обозначение `у.е.`:
- цена товара и отдельные цены в списках — формат `N0` (например, `4 990 у.е.`);
- средняя цена — формат `N2` (например, `4 415,00 у.е.`), поскольку среднее значение может быть дробным;
- разделитель тысяч, десятичный разделитель и обозначение единицы измерения едины во всех разделах вывода.

`PriceFormatter` намеренно остаётся `file`, как прямо требуется заданием. Поэтому `Product` и `CatalogReport` не вызывают этот тип, а используют тот же явно заданный формат и ту же культуру. Это сохраняет демонстрацию области видимости `file`, не создавая зависимости доменного слоя от презентационного слоя.

## 8. Компоновка и сценарии в `Program.cs`

Корневой `Program.cs` выполняет последовательную демонстрацию:

1. Создаёт четыре корректных товара и добавляет их в каталог.
2. Проверяет некорректный ID, пустое название, отрицательную цену, отрицательную цену через `SetPrice(-100)`, дублирование названия и `Add(null)`.
3. Выполняет успешный поиск и поиск отсутствующего товара; удаляет существующий товар и проверяет `Remove` для отсутствующего.
4. Передаёт найденный из каталога товар в `Cart`, добавляет количество и рассчитывает стоимость. Так показана связь нового каталога с корзиной из предыдущего этапа.
5. Получает `IReadOnlyList<Product>` и показывает контракт только для чтения. Попытка вызвать `Clear()` оставлена в отчёте как намеренно некомпилируемый пример, чтобы основной проект оставался собираемым.
6. Сохраняет и загружает каталог через `IProductRepository`.
7. Печатает список и топ товаров через `CatalogPrinter`, формирует сводку через `CatalogReport`.

Проверки, которые должны завершаться исключением, выполняются через `try/catch`; некорректные данные не изменяют существующие объекты и каталог.

## 9. Доказательство инкапсуляции: ошибки компилятора

Эти фрагменты **не нужно оставлять в основном `Program.cs`**, иначе проект перестанет собираться. Они предназначены для отдельной проверки и фиксации диагностик компилятора в отчёте.

### 9.1. Попытка напрямую изменить закрытое поле товара

```csharp
Product product = new Product(10, "Тест", 100);
product.price = -100;
```

Ожидаемая диагностика компилятора: **CS0122** — поле `Product.price` недоступно из-за уровня защиты (`private`). Поле можно изменить только изнутри `Product`; внешний код должен пользоваться публичным методом `SetPrice`, который проверяет значение.

### 9.2. Попытка изменить коллекцию каталога

```csharp
Catalog catalog = new Catalog();
catalog.GetProducts().Clear();
```

Ожидаемая диагностика компилятора: **CS1061** — у `IReadOnlyList<Product>` нет определения `Clear` и подходящего метода расширения. Это compile-time доказательство того, что публичный контракт не предоставляет операцию изменения списка.

### 9.3. Проверка SetPrice во время выполнения

В отличие от двух предыдущих примеров, этот код компилируется, но выбрасывает исключение:

```csharp
Product product = new Product(10, "Тест", 100);

try
{
    product.SetPrice(-100);
}
catch (ArgumentOutOfRangeException ex)
{
    Console.WriteLine(ex.Message);
}
```

В основном `Program.cs` эта проверка выполняется автоматически. После отклонения отрицательной цены значение `GetPrice()` остаётся равным исходному.

## 12. SRP и DIP в проекте

**SRP — принцип единственной ответственности:**
- `Product` хранит и валидирует состояние товара;
- `Catalog` управляет набором товаров;
- `FileProductRepository` отвечает за файловое сохранение и загрузку;
- `CatalogPrinter` отвечает за вывод;
- `CatalogReport` отвечает за вычисления.

Ни `Product`, ни `Catalog` не печатают данные и не работают с файлами.

**DIP — принцип инверсии зависимостей:**

Точка входа использует переменную типа `IProductRepository`. Контракт отделён от реализации: при появлении другого репозитория можно реализовать тот же интерфейс и заменить создание объекта в точке композиции, не переписывая код сохранения и загрузки, который работает через интерфейс.

В ходе работы закреплено, что модификаторы доступа формируют границы публичного контракта. `private` защищает внутренние поля и вспомогательные методы; `internal` ограничивает реализацию рамками сборки; `file` ограничивает вспомогательный тип одним исходным файлом; `public` используется для типов и операций, которые должны быть доступны другим слоям.

Инкапсуляция не позволяет внешнему коду напрямую присваивать недопустимые значения полям товара или менять внутренний список каталога. Вместо этого внешние компоненты используют контролируемые методы `SetPrice`, `Add`, `Remove`, `Find` и `GetProducts`.

Разделение на `Domain`, `DataAccess` и `Presentation` делает назначение компонентов понятным. Интерфейс `IProductRepository` отделяет клиентский код от способа хранения, а отдельные `CatalogPrinter` и `CatalogReport` показывают разделение печати и расчётов по SRP. Сохранённая корзина из предыдущего задания использует товар, найденный в новом каталоге, что связывает этапы проекта без искусственного удаления старой функциональности.
